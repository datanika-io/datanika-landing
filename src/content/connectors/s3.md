Amazon S3 is the most common file-based source — teams use it to ingest CSV exports, Parquet data lake files, JSON event logs, and third-party data drops into their warehouse. Datanika reads files from S3 using the dlt filesystem source, which handles pagination, glob patterns, and schema inference automatically.

> **S3 is source-only.** You can read files from S3 but can't use S3 as a destination in Datanika.

## Prerequisites

- A **Datanika account** with permission to create connections.
- A **destination warehouse** already connected.
- An **AWS account** with an S3 bucket containing the files you want to sync.
- **IAM credentials** with `s3:GetObject` and `s3:ListBucket` permissions on the target bucket.

## Step 1 — Create IAM credentials

1. In the AWS Console, go to **IAM → Users → Create user**.
2. Name it `datanika-s3-reader`.
3. Attach a policy with minimum permissions:
   ```json
   {
     "Version": "2012-10-17",
     "Statement": [{
       "Effect": "Allow",
       "Action": ["s3:GetObject", "s3:ListBucket"],
       "Resource": [
         "arn:aws:s3:::<your-bucket>",
         "arn:aws:s3:::<your-bucket>/*"
       ]
     }]
   }
   ```
4. Create an access key: **Security credentials → Create access key → Third-party service**.
5. Copy the **Access Key ID** and **Secret Access Key**.

> **Least privilege.** `GetObject` + `ListBucket` is all Datanika needs. No write, delete, or bucket management permissions.

## Step 2 — Add the connection in Datanika

1. In Datanika, open **`/connections`** and pick `s3` from the type dropdown at the top of the inline New Connection form.
2. Fill in:
   - **Connection Name** — a label for this connection, e.g. `s3-data-lake`.
   - **Bucket URL** — `s3://<your-bucket>` or `s3://<your-bucket>/path/prefix/`
   - **AWS Access Key ID** — from Step 1 (optional if running on EC2 with an IAM role)
   - **AWS Secret Access Key** — from Step 1 (optional with IAM role)
   - **Region** — e.g. `us-east-1` (optional, auto-detected from bucket)
   - **Endpoint URL** — only needed for S3-compatible stores (MinIO, Backblaze B2, etc.)
3. Click **Test Connection** — Datanika verifies it can list the bucket with the provided credentials.
4. Click **Create Connection**.

## Step 3 — Configure the upload

Extract-load is configured at **`/uploads`**, not on the connection. There is no "Configure pipeline" button — connection rows offer only Test / Edit / Copy / Delete, and `/pipelines` is the **dbt** builder, which is a different thing.

1. Open **`/uploads`**. The **New Upload** form is rendered inline on the page.
2. Fill in **Upload name** (letters and digits only — anything else is stripped as you type, so `s3-daily-load` becomes `s3dailyload`) and an optional **Description**.
3. Pick the **Source connection** and the **Destination connection** — the S3 connection from Step 2 is the source. Each picker opens a dialog listing entries as `16 — myconnection (postgres)`, i.e. id, name, type.
4. **File Pattern** — an input placeholdered `*.csv, *.json, or custom pattern`. A glob applied **underneath** the bucket URL on the connection — so the connection points at a prefix (`s3://my-bucket/exports/`) and this narrows it (`*.csv`). A pattern that matches nothing still completes as `success` with 0 rows ([core#493](https://github.com/datanika-io/datanika-core/issues/493)), so check the row count on the run.
5. Click **Create Upload**. It appears in the table below with status `draft`.

> **There is no write disposition, load mode, source schema or table-name field for a S3 source, and that is deliberate.** Those controls are rendered only when the source is a SQL database.

> **Batch size** (default 10000) and the optional **Schema Contract** dropdowns — **Tables** / **Columns** / **Data Type** — are on every upload regardless of source. The contract decides whether a changed incoming shape evolves the destination or fails the run.

## Step 4 — First run

1. On the **`/uploads`** row for your upload, click **Run**. There is no "Run now" on a pipeline page — the trigger lives on the upload's own row.
2. Watch **`/runs`**. The run shows a status badge, start and finish timestamps and a **Rows** count; the **Logs** icon on the row opens the detail.
3. When it finishes, open **Catalog** and browse the landed tables. The upload lands them in a schema **named after the upload** — `s3dailyload` creates schema `s3dailyload` in the destination, next to dlt's `_dlt_loads` / `_dlt_pipeline_state` / `_dlt_version` bookkeeping tables. There is no target-schema field to choose.
4. Spot-check the row count against the source. **Verify in the destination rather than trusting the status badge** — a green run means the load finished, not that it moved what you expected.

## Step 5 — Schedule it

Schedules live on their own page and reference the upload **by name**.

1. Open **`/schedules`**. The **New Schedule** form is rendered inline.
2. Fill in:
   - **Target type** — `upload` (the dropdown also offers pipelines and transformations).
   - **Target name** — the upload's name exactly as it was saved, e.g. `s3dailyload`.
   - **Cron expression** — a real five-field cron string. There is no cadence picker and no "manual only" option: leaving the upload unscheduled *is* manual-only. `0 * * * *` hourly, `0 */6 * * *` every six hours, `0 3 * * *` nightly at 03:00.
   - **Timezone** — defaults to `UTC`. The cron is evaluated in this zone, which matters for daily and weekly cadences.
3. Click **Create Schedule**. The row lands as **Active**, with **Pause** available per row.
4. Wire up failure alerts in **Settings → Notifications** so you hear about broken runs before your stakeholders do.

## Troubleshooting

### `Access Denied`
**Fix.** Verify the IAM policy has `s3:GetObject` + `s3:ListBucket` on both the bucket ARN and `bucket/*`.

### No files found
**Fix.** Check the bucket URL prefix and file glob pattern. The glob is relative to the bucket URL — if your bucket URL is `s3://my-bucket/data/` and your glob is `*.csv`, it looks for `s3://my-bucket/data/*.csv`.

### Schema inference picks wrong types
**Fix.** For CSV files without headers, or with inconsistent types, dlt may infer incorrect column types. Check the first few files for consistency.
